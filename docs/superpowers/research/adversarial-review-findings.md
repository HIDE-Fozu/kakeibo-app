# critique-ux-scope
1. [high/backup] Manual-only backup on a fully-offline app with no iCloud/auto-export is a permanent data-loss trap. Lost/reset/reinstalled phone = entire financial history gone forever. Users reliably forget to run a manual share-sheet export, yet the app's whole value is longitudinal history. This is the single highest product risk and it is treated as a solved 'confirmed' decision.
   -> Separate 'no third-party servers/LLM' from 'no user-owned cloud backup'. Apple's iCloud private DB (or an automatic periodic JSON export to a user-chosen iCloud Drive folder) does NOT send data to your servers or an LLM and should be allowed. At absolute minimum add a recurring local reminder to back up and surface 'last backup: N days ago' prominently. Do not ship v1 on manual-only backup.
2. [high/ux-scope] The daily input loop — the make-or-break of any kakeibo app — is under-designed. EntryForm is described as 6 equal-weight fields (type toggle/amount/date/category/payment/memo) with no fast numpad, no category quick-grid, no 'save and add another', no recently-used ordering. Best-in-class apps (Zaim/MoneyForward) open straight to a large keypad + icon grid. Six standard inputs per coffee purchase kills daily adoption.
   -> Design a dedicated fast-entry path: custom numeric keypad focused on open, category as a tappable icon grid ordered by most-recently/most-used, amount+category as the only required interactions, memo/payment collapsed by default, and a 'save & add another' action. Treat this as the core feature, not a generic form.
3. [high/ux-scope] Edit and delete of an existing transaction are entirely absent from screens and flows. Tapping a transaction in the day list has no defined behavior, and there is no delete affordance anywhere. This is table-stakes, not YAGNI, and it silently introduces a THIRD mode of the 'shared' EntryForm (edit-existing with delete + updatedAt bump).
   -> Explicitly define tap-to-edit (reuse EntryForm in edit mode with a delete button) and swipe-to-delete in the day list, with an undo/confirm. Update the '違いはプリフィルだけ' claim to account for edit mode and its delete/validation differences.
4. [high/architecture] 'EntryForm differs only by initial prefill' (§③) directly contradicts §⑤/§⑧, where the receipt-confirm path needs confidence-colored highlights, a 'requires review' state, and recovery when the parser grabbed the wrong number. It also has no receipt image reference, because the model has no image field — so the user cannot cross-check the confirm screen against the actual receipt. The receipt-confirm surface is materially more than prefill.
   -> Acknowledge receipt-confirm as a distinct mode layered on the shared form: confidence highlights, a way to cycle through detected amount/date candidates when the top pick is wrong, and (transiently) show the captured image during confirm. Reconcile §③ with §⑤/§⑧ so the 'only prefill' claim isn't load-bearing.
5. [high/ux-scope] Date semantics on manual FAB entry are ambiguous under a calendar-first model. If the user is viewing July 1 in the calendar and taps the global FAB, does the new entry default to the selected day (July 1) or to today (July 3)? Calendar-first strongly implies context-carry, but a global FAB implies today. Either choice surprises users half the time and is a classic silent-misentry bug.
   -> Decide and document: when a specific day is selected in the calendar, FAB entry should default its date to that selected day (with the date field clearly shown/editable); otherwise default to today. Make the defaulted date visible so mis-dating is caught at a glance.
6. [high/backup] Import is destructive full-replace (全消し→投入) with no merge. Exporting on phone A, adding entries on phone B, then importing A wipes B's entries. It also can't restore a single accidentally-deleted transaction without nuking everything. The pre-import auto-退避 mitigates catastrophe, but where that safety file lands and how a panicking user retrieves/re-imports it is undefined.
   -> Frame this feature as 'Restore (replaces all data)', not 'Import', with an unmissable destructive-action confirm. Define exactly where the auto-退避 file is written and give a one-tap path to re-import it if restore goes wrong. Consider a simple additive/merge-by-id import as the real need for moving between devices.
7. [medium/data-model] paymentMethod is over-scoped for v1. Card-import was cut, and there is no payment-method breakdown anywhere in Summary — so the field yields zero analytical value while adding a column to the model and a field to every entry form. Worse, its default (現金/cash) is backwards for this specific user, who spends via 楽天/セゾン/ビュー + PayPay + Suica, forcing a constant manual change or leaving it wrong.
   -> Drop paymentMethod from the v1 EntryForm UI (keep a nullable column if you want future-proofing without migration). If kept at all, default to last-used rather than cash. Don't tax the highest-frequency screen for a field nothing reads.
8. [medium/ux-scope] Calendar-as-home is a review/browse model imposed on an input-first job. The home screen's prime real estate serves the secondary task (looking back), while the primary task (adding today's spend) is a floating button behind a two-step FAB menu. This is the riskiest product hypothesis in the design, yet it is marked 確定 and unexamined against a 'today + quick add' home.
   -> Pressure-test the calendar-home bet before locking it. Consider a home that leads with today's running total + a recent-entries list + prominent add, with the month calendar one tap away. If calendar stays home, make the add path a single tap, not FAB→menu→choice.
9. [medium/ux-scope] The FAB double-choice ('手入力' vs 'レシートから') taxes the ~95% common path (manual entry) with an extra decision to serve the ~5% path (receipt, which for a cash-receipt-only OCR is even rarer). Coequal billing of the two inverts frequency.
   -> Make FAB open manual quick-entry directly; put the camera/receipt trigger as a secondary button inside the entry surface (or a long-press / small camera icon). Optimize taps for the dominant action.
10. [medium/ux-scope] Calendar month-cell legibility is at risk. Each cell rendering 支出合計 (plus net) means 4-5 digit yen figures (family 食費 alone can be ¥8,000+/day) in ~45px-wide cells across a 6x7 grid — cramped, noisy, and often illegible on a phone. The exact-number-per-cell decision isn't validated.
   -> Decide the cell representation deliberately: abbreviated (¥12k), a magnitude dot/bar heatmap, or expense-only with net shown only in the month header. Prototype on a real device with realistic 5-digit amounts before committing.
11. [medium/ux-scope] Empty states and onboarding are barely specified (one bullet). Concretely missing: first-launch experience (silent preset seeding leaves an empty calendar with no guidance to the FAB), empty Summary (a donut of nothing), empty-day tap, and — critically — no onboarding that teaches backup. On a manual-backup offline app, a user who never learns to export is one reinstall from total loss.
   -> Design each empty state with a clear CTA (empty calendar/day → 'Add your first entry', empty summary → friendly prompt). Add a lightweight first-run that explains offline + the backup responsibility, and nudges an initial backup once data exists.
12. [medium/data-model] The receipt image is never persisted (no imagePath in Transaction; source=receiptOcr only). After parse the image is discarded, so a user who later notices OCR grabbed the wrong total has no way to re-verify, and the confirm screen has no image to check against. This is a real constraint hiding as an omission.
   -> Make an explicit decision: either persist an optional local image reference (storage/privacy cost, but enables re-verification and a richer confirm screen) or document that images are intentionally transient and accept that OCR errors are unrecoverable after save.
13. [medium/parser] '各抽出値に確信度を持たせ色分け' is undefined. A regex either matches or not; deriving a meaningful confidence from keyword proximity/fallback-vs-keyword needs a concrete scoring rule, or the color highlights are arbitrary and erode trust rather than build it.
   -> Define confidence as discrete, explainable tiers (e.g., high = amount adjacent to 合計/計 keyword on same line; medium = keyword-less max-value fallback; low = no candidate/defaulted-to-today date) and map each tier to a color. Keep it rule-based and testable, not a numeric black box.
14. [medium/testing] Sequencing risk in the test strategy: ReceiptParser is to be built and validated on Windows first, but real Apple Vision output (with its real noise, line-splitting, and coordinates) can only be captured via the Mac bridge tool after the iOS channel is built. Parser heuristics tuned to hand-authored fixtures risk overfitting to fake data and missing real OCR failure modes.
   -> Do a small upfront Mac spike (or even run a batch of ~15 real photographed receipts through Vision once) to capture genuine OCR-output fixtures BEFORE investing in parser heuristics. Order the work so parser tuning is driven by real fixtures, per §⑨'s own homework.
15. [low/ux-scope] A single receipt maps to one Transaction with one category, but real supermarket/drugstore receipts routinely span 食費 + 日用品 + 医療. v1 forces one category for the whole receipt. This may be acceptable YAGNI, but it is an undocumented limitation that will surprise the exact users OCR targets.
   -> Explicitly document 'one receipt = one entry, one category' as a v1 limitation, and make it trivial to add a second manual entry for the split portion (e.g., 'save & add another' pre-filled with the same date/store).
16. [low/backup] CSV round-trip and dual serialization are lightly over-scoped and under-specified. §⑦ tests BackupService '往復', but §7's model is JSON=restore / CSV=view-only, so CSV likely shouldn't round-trip at all. Meanwhile CSV export must escape memo/店名 fields containing commas/newlines/quotes and pick an encoding (Excel-JP Shift-JIS vs UTF-8 BOM), or files break on open.
   -> Clarify JSON is the only round-trip format (test 往復 on JSON only); treat CSV as export-only and consider deferring it to Phase 2. If CSV ships, spec RFC-4180 escaping + UTF-8-with-BOM (or Shift-JIS) explicitly and test with commas/newlines in memo.
17. [low/data-model] Category-delete offers two competing strategies (archive OR reassign to 未分類) in §⑧, which is indecision that doubles code paths, and 未分類 requires a special protected category. The income/expense toggle also silently must refilter the category list and reset the selection, an unspecified interaction that is a common bug source.
   -> Pick one delete strategy for v1 — archive (keeps history intact, simplest) — and drop the 未分類 reassignment path. Specify that flipping the type toggle refilters categories and clears the selected category, and cover it with a test.

# critique-data-backup
1. [high/backup] Replace-on-import (全消し→投入) is not specified to be atomic. If DELETE-ALL succeeds but the subsequent INSERT batch fails partway (malformed row N of M, FK violation, disk full, app killed/backgrounded by iOS mid-write, or an exception in the CSV path), the user is left with all prior data deleted and only a partial restore — total or near-total data loss.
   -> Wrap the entire delete+insert in a single drift transaction so any failure rolls back to the pre-import state. Better: parse+fully validate the whole import payload into memory FIRST, then delete-then-insert inside one transaction (validate-then-swap). Never delete before the new dataset is proven insertable.
2. [high/backup] The pre-import '自動退避エクスポート' safety net is underspecified in every load-bearing dimension: where it is written, whether the write is verified before the destructive delete runs, its format fidelity, retention, and how a user restores from it. Export normally uses the share sheet (needs user interaction) — an auto-backup cannot; it must be a silent local write. If that silent write fails (no space/permission) or is lossy, the delete still proceeds and the net is illusory.
   -> Auto-backup must: (1) write silently to app storage as full-fidelity JSON, never CSV; (2) verify the file exists and re-parses cleanly BEFORE proceeding to delete, aborting import otherwise; (3) be timestamped and NOT overwrite prior auto-backups (a chain of bad imports must not erase the last-good state); (4) be reachable via a 'restore from auto-backup' UI, or the user cannot recover after a bad import.
3. [high/data-model] date is 日単位 (day only) but the model gives no storage encoding. drift's default DateTimeColumn stores a UTC unix timestamp. A value entered as 2026-07-02 00:00 JST is stored as 2026-07-01 15:00 UTC; on JSON round-trip, tz change while traveling, or a DST locale, it renders/buckets as the previous day. DateTime.now() also carries a time component, so two 'same-day' entries may not compare equal and calendar/summary day-grouping can bucket into the wrong day.
   -> Store date as a timezone-free civil date: TEXT 'YYYY-MM-DD' or an integer day-count, never a timestamp. Normalize on entry (strip time). Serialize as a plain date string in JSON and CSV. Keep createdAt/updatedAt as explicit UTC ISO-8601 and never reuse them as the transaction date.
4. [high/backup] CSV sits in the import/restore path yet is fundamentally lossy, and the doc contradicts itself: line 88 labels CSV '表計算閲覧用' (viewing) and JSON '正確な復元用' (accurate restore), but item 7, section ①, and the summary list JSON/CSV as co-equal import formats. CSV is single-table so it cannot represent Transaction+Category with FK ids, icon, sortOrder, isArchived; re-import must re-derive categories by name → duplicates and lost attributes. CSV also cannot carry schemaVersion, so CSV import silently bypasses schema validation.
   -> Make CSV strictly export-only (viewing/analysis) and remove it from the import/restore path; JSON is the sole restore format. If CSV import is truly required, document it as lossy, forbid it as the auto-backup format, and gate it behind explicit schema/column validation — but the cleaner v1 decision is export-only.
5. [high/data-model] Category integrity has three coupled holes, all in the unapproved draft ⑧: (1) the '未分類へ再割当' fallback references an Uncategorized category that does not exist in the model or preset list and has no stable id — reassigning to a non-existent category orphans transactions; (2) Category.type is user-editable, so changing a category expense→income desyncs it from existing Transaction.type and corrupts expense/income aggregation; (3) SQLite foreign_keys PRAGMA is OFF by default and drift enablement is not stated, so a hard category delete can leave dangling categoryId that crashes summary joins.
   -> Define a permanent, non-deletable '未分類' sentinel per type with a fixed reserved id, seeded on first run and guaranteed present after every import. Block (or cascade-with-warning) category type edits when transactions exist. Confirm PRAGMA foreign_keys=ON in drift, make categoryId a NOT NULL FK with an explicit ON DELETE policy (RESTRICT + app-level archive/reassign).
6. [medium/backup] schemaVersion is described only as 'validate', presumably equality. Backups are a long-term safety net, but once the app ships a schema migration and bumps the version, every older backup becomes unrestorable (rejected by strict equality), defeating the purpose. Conversely a file from a NEWER app version imported into an older build must be rejected, not best-effort parsed.
   -> Support forward-migration of import payloads across a documented range of older schemaVersions (transform old JSON → current shape before insert). Explicitly reject files newer than the app. Treat missing/zero schemaVersion as invalid, not as 'assume current'.
7. [medium/backup] Whether import preserves record ids or regenerates them is unspecified. If categories are re-inserted with new ids while Transaction.categoryId values are copied verbatim (or vice versa), every transaction points at the wrong or a missing category — a silent corruption that passes a naive 'row count matches' check.
   -> Preserve original ids on import (clean-slate replace makes this safe), or if remapping, build an old→new id map for categories and rewrite every Transaction.categoryId through it inside the same transaction. Add a post-import assertion that every categoryId resolves.
8. [medium/data-model] Archived categories still own historical transactions. If summary/calendar aggregation joins filter out isArchived categories (the natural way to hide them from pickers), those transactions vanish from category breakdowns while possibly still counting in the grand total — subtotals no longer reconcile to the monthly total. Concrete: user archives 外食 after ¥50,000 of spend; the summary donut drops ¥50,000 or shows an empty slice.
   -> isArchived must affect only the category PICKER, never aggregation. Keep archived categories in all historical rollups (labelled 'archived'). Add an invariant/test: sum of per-category subtotals == grand total for any month.
9. [medium/backup] Only a destructive replace import exists — no merge/append. The stated transport is the share sheet over iCloud Drive/email (line 45), which implies moving data between devices. A user who exports from an old phone and imports on a phone that already has entries will silently lose the on-device entries, expecting a combine.
   -> Make replace semantics unmistakable in the confirm dialog ('this ERASES all current data and replaces it with the file — N transactions will be deleted'), showing current-vs-incoming counts. Consider a merge/append mode post-v1; at minimum prevent the silent-wipe surprise.
10. [medium/backup] Validation before the destructive delete appears limited to schemaVersion. A file with the correct version but corrupt content (non-integer amount, unknown type/paymentMethod enum, unparseable date, categoryId with no matching category, or an empty transaction array from a truncated export) can pass the version gate and then wipe existing data during a doomed insert.
   -> Before deleting anything, validate the full payload: amounts are non-negative integers, type/paymentMethod are known enums, dates parse as civil dates, every categoryId resolves to an included category, and the dataset is non-empty (or explicitly confirm an empty-restore). Reject and keep existing data on any violation.
11. [medium/parser] There is no representation for refunds/returns/negative amounts. With amount a non-negative integer disambiguated only by type(expense/income), a store refund has no clean home, and every aggregation must correctly branch on type. A single query that sums amount without a type filter (e.g. a day-cell total or category rollup) will double-count or sign-flip the net (差引). Separately the OCR parser strips 'お預り/お釣り/現金' but a change-giving cash receipt where total < tendered can still surface a wrong max-value fallback.
   -> Decide refund handling explicitly (negative-allowed amount, or a dedicated refund type). Centralize signed-amount logic in one repository helper so no screen re-derives sign; add tests asserting net = income_sum − expense_sum on mixed data and refund cases.
12. [medium/backup] CSV encoding/escaping for Japanese is unaddressed. UTF-8 without BOM renders as 文字化け in Excel; and if any memo/店名 contains a comma, double-quote, newline, or emoji (e.g. 'セブン-イレブン, 渋谷店' or a multiline note), naive CSV writing shifts columns and a subsequent re-import maps values into the wrong fields.
   -> If CSV stays (even export-only), use RFC-4180 quoting/escaping via a real CSV library and emit UTF-8 with BOM for Excel. This reinforces keeping CSV out of the restore path so escaping bugs cannot corrupt a restore.
13. [low/testing] The BackupService round-trip test (export→import→一致) runs under Windows flutter test in the host machine's single timezone. The most likely real defect — a tz/DST day-shift in date storage/serialization — will NOT reproduce there because export and import share the same host tz. The very test meant to guarantee round-trip fidelity can pass green while a JST device loses or shifts a day.
   -> Make round-trip tests tz-hostile: run cases under multiple TZ settings (UTC, Asia/Tokyo, a US tz) and assert date equality as civil-date strings, plus 23:59 and 00:00 boundary cases. Add a fixture exported in JST that must resolve to the same calendar day after import in another tz.
14. [low/data-model] source=receiptOcr is recorded but Transaction has no imagePath — the captured receipt is discarded. Defensible for offline/privacy, but a saved OCR entry can never be re-audited or re-parsed if the parser later improves, and there is no evidence trail. Separately, edit provenance is undefined: after a user hand-corrects an OCR entry, does source stay receiptOcr, and is updatedAt reliably bumped on every edit path (needed for any future merge/reconcile)?
   -> Confirm the intentional no-image decision in writing. Define edit semantics: keep source as immutable origin-provenance (or add an 'edited' flag) and guarantee updatedAt is set on every mutation via a single repository choke point rather than per-screen.

# critique-parser-offline
1. [high/offline] The only backup path exports the ENTIRE financial DB as plaintext JSON/CSV through the iOS share sheet to iCloud Drive / メール. iCloud Drive is cloud storage and email traverses third-party servers, so the sole durability mechanism puts 100% of financial data off-device — a direct contradiction of decision #1 ("データを外に出さない＝完全オフライン"). The export is unencrypted, so a compromised iCloud account or a forwarded mail leaks everything. The design silently equates 'no cloud SYNC service' with 'offline' while shipping a cloud EXPORT path.
   -> Redefine 'offline' precisely as 'no automatic/background/LLM exfiltration; user-initiated export leaves the device by design.' Add passphrase-based encryption (AES-GCM/age) over the JSON export as the default; warn in-UI that iCloud/メール are cloud destinations; make 'Save to Files (on-device)' the default share target.
2. [high/backup] DB is local-only SQLite, import is wipe-then-load (置換) with NO merge, backups are fully manual, and iOS deletes the app sandbox on uninstall. A lost/reset phone, an accidental uninstall, or 'restore an old backup after entering new data' all cause irrecoverable loss. Notifications are explicitly out of scope, so nothing nudges the user to export. The 取込前自動退避 export's destination and recovery UX are unspecified — if it also requires the share sheet it is not actually automatic.
   -> Add an on-device automatic periodic export to the app's Files container (independent of the share sheet); define the auto-safety-export destination plus a one-tap 'undo last import'; offer a merge/upsert-by-id import mode so restoring never clobbers newer rows; show an in-app 'last backup N days ago' banner since notifications are excluded.
3. [high/parser] The priority keyword set mixes 合計(税込) with 小計(税抜), 計, and お買上げ, which defeats the stated '税込採用.' On the canonical layout 小計¥1,000 / 消費税¥80 / 合計¥1,080, treating 小計 and 合計 equally lets the parser pick the tax-EXCLUDED 小計. On 外税 receipts printing both 税抜合計 and 税込合計, matching the first '合計' selects the tax-excluded one. 'お買上げ' also appears in the thank-you line and in 'お買上点数 5点' (grabs the item count 5).
   -> Rank labels: 合計/お会計/税込合計/ご請求 as total; explicitly DEMOTE/EXCLUDE 小計 and 税抜合計 from total candidates; match whole labels rather than the substring 計 (which also hits 合計点数/課税計/非課税計). When 小計+消費税+合計 all parse, assert 合計≈小計+税 and pick the tax-inclusive line; when two 合計 differ, pick the larger.
4. [high/parser] The max-value fallback's exclusion list is only お預り/お釣り/現金. It omits ポイント残高, 電子マネー残高 (WAON/nanaco/Suica), 今回付与ポイント, and any P-suffixed value. Drugstore/point-card receipts routinely print ポイント残高 15,000P or 残高 ¥12,340 that exceed the purchase total; if OCR drops the P/残高 label, the max-value fallback selects the balance as the total. お預り (e.g., paid 10,000 for a 1,080 purchase) also beats the total, and the keyword-association exclusion is exactly what OCR noise (御預り/預り金/misread label) breaks — so the exclusion fails precisely on the fallback path where it matters.
   -> Expand exclusions to ポイント/pt/P/残高/釣/預/入金/チャージ/前回, and drop any candidate with a P suffix or on a 残高 line; never use max-value when a 合計 keyword exists; when falling back, prefer the amount consistent with the item-line sum, not the global max.
5. [high/architecture] The parser's '最上部（発行日）優先' and '同一行右側・近傍' logic depends on coordinate origin/axis/units, but TextBlock{text, boundingRect} defines none. Apple Vision returns normalized coords with BOTTOM-LEFT origin (y up); ML Kit returns pixel coords with TOP-LEFT origin (y down). It also leaves granularity (line vs block) and page rotation undefined. Swapping to ML Kit — an explicit design goal ("将来 ML Kit も差し替え可") — would silently invert top/bottom and misalign rows with no compile error: date picks the bottom-most date, amounts match the wrong row.
   -> Specify TextBlock in a canonical space (top-left origin, y-down, normalized 0–1, deskewed/upright, line granularity) and make each OcrService adapter convert into it; document and unit-test the convention; also surface per-block OCR confidence so 確信度 uses real signal rather than only keyword presence.
6. [high/parser] Since Oct-2023 every receipt prints a mandatory インボイス登録番号 'T + 13 digits', plus TEL, 〒郵便番号, 取引/レジ/責任者番号, JAN codes, and date-time. The bare-number regex (`1234`) captures fragments of these; a split 13-digit T-number or a phone number can exceed the total and win the max-value fallback, or a stray number adjacent to a keyword gets grabbed. The design (dated 2026) does not mention invoice-number pollution at all.
   -> Require a currency cue (¥/￥/円/comma-grouped 3 digits) for a candidate to be eligible as an amount; blacklist lines matching T\d{13}, TEL/電話, 〒, 登録番号, No./レジ/責任者, and date/time patterns; treat bare integers without a currency cue as lowest-confidence only.
7. [medium/parser] Many receipts print the Reiwa year as a bare digit ('6.07.03' = 令和6年 = 2024) with no 令和/R label. The `YY.MM.DD` rule parses 6 as 西暦下2桁 → 2006, an 18-year error. The era table (令和/平成/昭和, R/H/S) is also implied but not specified; 令和N→2018+N.
   -> Add era inference: a 1–2 digit leading year with no century, that is ≤ the current Reiwa year and would otherwise land ~18+ years in the past, is more likely wareki — reconcile against 'today' (reject >~1yr future or implausibly old); support 令和/平成/昭和 and R/H/S prefixes; when ambiguous, mark low-confidence and default to a plausible recent date rather than 2006.
8. [medium/parser] '最上部優先' grabs the wrong date. The topmost date is frequently a promotional header (セール期間 7/1〜7/7, ○/○まで有効) or, on credit slips, the card 有効期限 MM/YY — all sit above or apart from the actual 取引日/レジ打刻 date. Pure y-position selection picks these over the purchase date.
   -> Anchor date selection to proximity with transaction cues (レジ/No./時刻 HH:MM/責任者) rather than raw y-position; exclude ranges (A〜B) and 有効期限/まで/期限 lines; prefer a date co-located with a time stamp.
9. [medium/parser] Discounts are ignored, overstating the expense. With 小計1,000 / 値引-100 / 合計900, or a coupon 'クーポン値引 ▲500', if the parser lands on 小計 (or a pre-discount total) the recorded amount is too high. Japanese receipts use minus forms the regex will miss: ▲100, △100, trailing '100-', and parenthesized (100).
   -> Recognize negative/discount tokens (▲ △ leading- 値引 割引 クーポン, trailing minus, parentheses) and always source the amount from the post-discount 合計/お会計 line; where possible validate 合計 = Σitems − discounts + tax.
10. [medium/parser] Multi-total, tax-split, and dual-slip receipts under-determine 'keyword-adjacent.' Mixed 8%/10% receipts print 8%対象計 / 10%対象計 / 合計; コンビニ/クレジット paper prints the itemized 合計 AND a separate クレジット売上票 ご利用金額 合計; 返品 receipts carry NEGATIVE totals. Using the substring 計 also matches 合計点数 (grabs an item count like 5点) and 課税計/非課税計 (tax breakdown, not the total).
   -> Match whole labels not the 計 substring; when multiple total-like lines exist, pick the maximal tax-inclusive 合計/お会計 and reconcile duplicates (equal values = same txn); handle negative totals for returns explicitly; treat 対象計/課税計 as tax breakdown.
11. [medium/testing] The fixture bridge records the wrong layer and under-samples noise. ⑦ says record '実機のApple Vision出力' — if that is RAW Vision (bottom-left normalized, block granularity) but production feeds the parser a normalized TextBlock, tests exercise a coordinate/granularity space the parser never sees in prod (green tests, broken prod). Also a dozen clean recordings do not contain the OCR noise that breaks the heuristics (O/0 swaps, dropped ¥/P, merged/split lines, skew), so the self-test will over-estimate robustness — false confidence for the very 'AI self-test' the user relies on.
   -> Record fixtures at the exact normalized TextBlock boundary the parser consumes (post-adapter), snapshotting BOTH raw and normalized to catch adapter drift; add a synthetic perturbation layer (inject digit confusions, drop P/¥/label suffixes, merge/split/rotate blocks) to stress heuristics beyond the collected samples.
12. [medium/offline] Receipt images can leak to iCloud Photos even though Apple Vision itself is on-device. A receipt photo IS financial data; if image_picker/camera captures land in the shared photo library (or a backed-up temp path) and the user has iCloud Photos on, the images sync to cloud — undermining the offline promise. The design specifies no image lifecycle/retention.
   -> Capture to an app-private temp path (never the shared camera roll), parse, and delete immediately; exclude the temp path from iCloud backup where possible; document the image lifecycle explicitly.
13. [medium/parser] '同一行右側・近傍' has no defined tolerance and breaks on thermal-receipt skew/curl. Thermal paper curls and is photographed at an angle, so 'same line' by y-coordinate needs a tolerance that scales with size/rotation. Vision may merge '合計 ¥1,080' into one block or split label and amount into distant columns. An undefined tolerance either misses the amount (too tight) or grabs a neighboring row's number (too loose).
   -> Deskew/normalize before matching; define row-grouping tolerance as a fraction of median line height; explicitly handle both merged (label+amount in one block) and 2-column (label left / amount right, matched by nearest same-row block) layouts; unit-test both against fixtures.
14. [medium/data-model] Preset category re-seeding can collide with the replace-import. Import is wipe-then-load, but presets are auto-seeded on first run. If a fresh install seeds presets and then import wipes+loads categories with their own IDs — or the app re-seeds after import — ID/sortOrder collisions or duplicate presets occur, and every Transaction.categoryId FK must resolve exactly to an imported category. Since CSV is view-only, restore depends entirely on the JSON carrying full category records with stable IDs.
   -> Make import authoritative: on restore, disable preset seeding and load categories verbatim (IDs preserved); verify all Transaction.categoryId FKs resolve post-import and remap orphans to 未分類; require schemaVersion + a full category table in the JSON and reject CSV-only/partial restores.
15. [low/parser] No digit/character normalization for common OCR confusions (O/0, l/I/1, B/8, S/5, comma/period). '¥1,O80' or '1.080' fail the amount regex and drop a valid total, pushing the parser to a wrong fallback.
   -> Add a normalization pass in numeric contexts (O→0, l/I→1, B→8, S→5; unify thousands separators, and since JPY has no decimals treat any '.' as a separator artifact) before the amount regex; keep all JPY as integer yen.
16. [low/ux-scope] CSV export as plain UTF-8 renders Japanese category/店名 as mojibake in Japanese Excel (which expects Shift-JIS or UTF-8 with BOM), defeating the stated '表計算で閲覧' purpose on the most common tool.
   -> Export CSV as UTF-8 with BOM (or offer a Shift-JIS option); verify round-trip open in Japanese Excel and Numbers.
17. [low/parser] Partial dates (MM/DD only, common on short receipts) default the missing year to 'today's year,' mis-dating a late-December purchase scanned in early January by a full year.
   -> When the year is absent, pick the year that makes MM/DD nearest to but not after today (if MM/DD is in the future for this year, use last year); mark the value low-confidence.
