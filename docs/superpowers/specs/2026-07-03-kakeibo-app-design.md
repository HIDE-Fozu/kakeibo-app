## 1. 概要（何を作るか）

スマホ完結の個人向け家計簿。**カレンダー起点**で「その日の支出/収入を確認→素早く入力」し、**レシート撮影→金額・日付を自動抽出→確認して保存**できる。収入・支出の両方を月次集計。データは**端末内SQLite**に保持し、アプリが勝手に外部送信しない。

コア価値は「毎日の入力が速い」＋「後から履歴を振り返れる」。したがって設計の最優先は **(a) 日次入力ループの速さ**、**(b) データを絶対に失わない保全**、この2点。

## 2. コア原則

### 2.1 「完全オフライン」の再定義 【確定 §14-A: 再定義＋オンデバイス自動バックアップを採用】

当初の「データを外に出さない＝完全オフライン」は、実装すると自己矛盾する。**唯一の保全手段が「共有シートでiCloud Drive/メールに書き出し」だと、それ自体がクラウド送信**であり、しかも手動任意なので「再インストール/機種変/初期化で全履歴が永久消失」という最大の製品リスクになる（複数レビュアーが独立に最重要指摘）。

そこで原則をこう**精密化**して提案する:

> **アプリは、いかなる財務データも自動的・バックグラウンド的・第三者サービス/LLMに送信しない**（サーバも解析APIも持たない、テレメトリも無し）。**ユーザーが明示的に行うエクスポートだけが、ユーザーの意思で端末外に出る**。

この原則のもとで v1 に入れる保全策:
1. **サイレントなオンデバイス自動バックアップ**: アプリ専用のFilesコンテナ（共有シート不要）へ、フルフィデリティJSONを定期＆重要操作前に書き出し。**ローリング世代管理（直近N世代を保持、上書きしない）**。
2. **「前回バックアップ: N日前」バナー**をホーム/設定に常時表示（通知はv1非対象なので、これがバックアップ督促の代替）。
3. **エクスポートの任意パスフレーズ暗号化**（AES-GCM）。共有先がiCloud/メールでも中身が守られる。既定の共有ターゲットは **「ファイルに保存（端末内）」**。
4. **画像はカメラロールに残さない**（§7.6）。

> 補足: iCloud private DB（CloudKit）による端末間同期は「自社サーバ/LLMには出ない」ので原則には反しないが、v1ではスコープ肥大を避けて**採用しない**（Phase 2候補）。v1は「端末内DB＋オンデバイス自動バックアップ＋任意の暗号化エクスポート」で完結。

### 2.2 その他の確定原則
- **iOS のみ**（まず iPhone で完成）。
- **円のみ**・**金額は整数円**（浮動小数の誤差回避）。
- **日付は civil date（時刻なし・タイムゾーン非依存）**。§4.2 で厳守（重大バグ源）。
- **Riverpod / drift(SQLite) / table_calendar / image_picker / Apple Vision**。
- OCRエンジンは **`OcrService` 抽象**の裏に隔離（将来 ML Kit 差し替え可）。座標は**正準空間**に正規化してからパーサへ（§7.1）。

## 4. データモデル

### 4.1 テーブル

> **enum保存は `textEnum`（`.name`文字列）**。理由: 長期運用でenumに要素を挿入/並べ替えしても既存行が壊れない（`intEnum`の`.index`はシフトで破損）。以下の「enum」列は全てtextEnum。

**Transaction（取引）**
| 列 | 型 | 説明 |
|----|----|------|
| id | INTEGER PK | |
| type | TEXT enum | expense / income |
| amount | INTEGER | **整数円・非負**。符号はtypeで持つ（§4.4） |
| date | TEXT `YYYY-MM-DD` | **civil date**（§4.2）。`CivilDate`値型をTypeConverterで保存 |
| categoryId | INTEGER FK NOT NULL | Category.id、`ON DELETE RESTRICT` |
| paymentMethod | TEXT enum **nullable** | 【確定 §14-B】列は残し**v1入力UIには出さない**（将来マイグレ不要） |
| memo | TEXT | 店名・自由記述 |
| source | TEXT enum | manual / receiptOcr（**由来。編集しても不変**） |
| imagePath | TEXT nullable | 【確定 §14-C】既定は破棄。設定「ローカル保持」ON時のみ値が入る |
| createdAt | TEXT ISO-8601 UTC | |
| updatedAt | TEXT ISO-8601 UTC | 全更新経路で必ず更新（§9のリポジトリで一元化） |

**Category（カテゴリ）**
| 列 | 型 | 説明 |
|----|----|------|
| id | INTEGER PK | |
| name | TEXT | |
| type | INT enum | expense / income。**取引がある間は型変更をブロック**（集計desync防止） |
| icon | TEXT | 絵文字/アイコンキー |
| sortOrder | INTEGER | |
| isArchived | BOOL | **ピッカーからのみ隠す。集計には常に含める**（§4.3） |
| isSystem | BOOL | 「未分類」sentinel等の保護フラグ |

### 4.2 日付は civil date（重大バグ回避）
drift 既定の `DateTimeColumn` は **UTC unixタイムスタンプ**で保存する。`2026-07-02 00:00 JST` を入れると `2026-07-01 15:00 UTC` になり、JSON往復や旅行時のtz変化・DSTで**前日にバケットされる**。さらに `DateTime.now()` は時刻成分を持ち、「同じ日」の2件が等しく比較されない。

→ **`date` は `TEXT 'YYYY-MM-DD'`（またはepoch-day整数）で保存。入力時に時刻を捨てて正規化。JSON/CSVも日付文字列。** `createdAt/updatedAt` は別に UTC ISO-8601 で持ち、**取引日には絶対に流用しない**。月次クエリは文字列範囲（`date >= '2026-07-01' AND date <= '2026-07-31'`）で行う。

### 4.3 アーカイブと集計の不変条件
`isArchived` はカテゴリ**ピッカー**からの除外にのみ使う。アーカイブ済みカテゴリが持つ過去取引は**すべての集計に残す**（ラベルに「(アーカイブ)」を付す）。
- **不変条件（テスト化）**: 任意の月について「カテゴリ別小計の総和 == 月次グランド合計」。

### 4.4 符号（差引）と返品
`amount` は非負整数、収支は `type` で表す。**署名付き金額の導出はリポジトリの単一ヘルパに集約**し、各画面で再実装しない。
- 純額 `net = Σincome.amount − Σexpense.amount`。
- **返品/返金の v1 ルール（確定）**: `amount` は常に非負。負の金額は保存しない。返品は次のいずれかで表す — (a) 元取引を**編集して減額 or 削除**、(b) 対応する**返金を `type=income`（例: プリセット「その他」収入 or 返金用カテゴリ）として計上**。集計は `net` の定義でそのまま正しくなる。「支出カテゴリ内でマイナス支出として相殺表示」はv1非対象（YAGNI）。テストで mixed/返金ケースの `net` 符号を検証。

### 4.5 カテゴリ整合性（FK・未分類）
- **`PRAGMA foreign_keys = ON` を drift で明示**（既定OFF）。`categoryId` は NOT NULL FK・`ON DELETE RESTRICT`。
- **「未分類」sentinel を型ごと（支出/収入）に予約IDで初回シード**し、`isSystem=true`・削除不可。インポート後も必ず存在を保証。
- カテゴリ削除は **アーカイブのみ**（ハード削除しない）。「未分類へ再割当」の二重経路は採らない（indecision排除）。
- **型トグルの副作用を仕様化**: EntryFormで収入⇄支出を切り替えたら、カテゴリ候補を再フィルタし**選択中カテゴリをクリア**（未指定に）。テストで担保。

### 4.6 プリセットカテゴリ
- 支出: 食費／外食／日用品／水道光熱費／通信費／交通費／交際費／趣味・娯楽／衣服・美容／医療・健康／住居／教育／特別費／その他
- 収入: 給与／賞与／副収入／その他
- ＋ システム「未分類（支出）」「未分類（収入）」。
- 初回起動時シード。**復元時はプリセット再シードを無効化し、JSONのカテゴリをID保存でそのまま復元**（ID衝突・重複防止、§10.4）。

### 5.3 日付の既定（カレンダー起点の曖昧さ解消）
カレンダーで特定日を選択中にFAB入力→**その選択日を既定**にする。未選択なら**今日**。いずれも**日付欄を常に見えるように表示**して誤記録を一目で気づけるようにする。

### 5.4 EntryForm の3モード
「違いはプリフィルだけ」は誤り。実際は3モード:
1. **新規手入力**（空、日付=選択日/今日）
2. **レシート確認**（プリフィル＋**確信度ハイライト**＋**検出候補の切替**＋確認中は撮影画像を表示、§7）
3. **既存編集**（値ロード＋**削除ボタン**＋`updatedAt`更新、`source`は不変）
共通土台は同じでよいが、上記の差分を明示仕様化する。

### 5.5 空状態・初回
- 初回: プリセットを静かにシード後、**空カレンダーにFABへ誘導するCTA**。
- 空サマリ: 「まだデータがありません」＋入力導線。
- 空日タップ: 「この日に追加」。
- **初回に一度、オフライン方針とバックアップ責任を説明する軽量オンボーディング**。データが貯まったら初回バックアップを促す。

## 6. データフロー

### 6.1 手入力
FAB → 高速入力（日付=選択日/今日）→ 保存 → カレンダー/サマリ更新。

### 6.2 レシートOCR
入力面の副ボタン → カメラ/ギャラリー（**アプリ専用一時パス**へ取得、カメラロールに残さない）→ `OcrService` が正準TextBlock列を返す → `ReceiptParser`（純Dart）が金額・日付・確信度を抽出 → **EntryFormにプリフィル（自動抽出欄をハイライト、候補が複数なら切替UI、撮影画像を並置）** → ユーザーが店名・カテゴリ補完・修正 → 保存 → 画像は保持設定に従い破棄 or 保存（§14-C）。抽出失敗時は**空フォームにフォールバック**（金額欄フォーカス、注記）。

### 6.3 バックアップ／復元
- **自動（サイレント）**: 定期＋重要操作前に、アプリFilesコンテナへフルJSONを世代保存。
- **手動エクスポート**: 全取引＋カテゴリをJSON（任意暗号化）へ。CSVは閲覧用エクスポートのみ。共有シート（既定=ファイルに保存）。
- **復元**: 「復元（全データを置換します）」と明示。§10 の validate-then-swap で安全化。

## 7. ReceiptParser 設計（純Dart・自走テストの主対象）

入力: **正準化済み** `List<Block{ text, rect, confidence }>`（§7.1）。出力: `ParsedReceipt{ totalYen?, date?, totalConfidence, dateConfidence, debug }`。

### 7.1 正準TextBlock空間（差し替え耐性の要）
Apple Vision は **左下原点・正規化座標(y上向き)**、ML Kit は **左上原点・ピクセル(y下向き)**。パーサが原点を仮定すると、エンジン差し替えで上下が黙って反転する（date が最下部を選ぶ等）。
→ **正準空間を定義**: **左上原点・y下向き・0..1正規化・傾き補正済み(upright)・行(line)粒度**。各 `OcrService` 実装（AppleVision/MLKit/Fake）が自前でこの空間に変換する。**per-block OCR確信度も必須**（§7.5 の確信度に使う）。この規約は単体テストで固定。

### 7.2 金額抽出
1. **候補の資格ゲート（誤検出源を排除）**: 金額候補は**通貨手がかり必須**＝ `¥` / `￥` / `円` / **3桁カンマ区切り**のいずれかを伴うもののみを一級候補に。裸の整数（`1234`）は最低確信度でのみ。
   - **ブラックリスト行**: `T\d{13}`（インボイス登録番号・2023年10月以降必須）、`TEL`/電話、`〒`郵便番号、`登録番号`、`No.`/`レジ`/`責任者`、日付/時刻パターン。これらの数値は候補から除外。
2. **数字正規化**: OCR誤読 `O→0, l/I→1, B→8, S→5`、全角→半角、桁区切り統一。JPYは小数なしなので `.` は区切り誤読として扱う。→ 整数円。
3. **ラベル厳密ランク**（部分文字列 `計` でマッチしない。`合計点数/課税計/非課税計` を誤爆するため**語全体**でマッチ）:
   - **総額として採用**: `合計` / `お会計` / `税込合計` / `ご請求`。
   - **降格・除外**: `小計`（税抜）/ `税抜合計`。
   - 税込前提。`小計 + 消費税 + 合計` が揃うなら `合計≈小計+税` を検証して税込行を採る。`合計` が2つ（税抜/税込）あれば**大きい方**。
4. **同一行右側・近傍マッチ**: ラベル行の同一行（**行高の一定割合を許容tolerance**、傾き/カールに対応）右側の金額を優先。Visionが「合計 ¥1,080」を1ブロックに結合する場合と、ラベル左/金額右の2カラムに分割する場合の両方を扱う。
5. **フォールバック（ラベル無し）**: 資格を満たす候補から、**除外語に紐づく額を除いて最大**を採用。除外＝ `お預り/お釣り/現金/釣/預/入金/チャージ/前回` **＋ `ポイント/pt/P/残高`**（ポイント残高や電子マネー残高は総額を超えることがあり、ラベルOCR落ちで最大値誤採用の主因）。ラベル `合計` がある時は**maxフォールバックを使わない**。
6. **クロス検証**: `お預り`(T)と`お釣り`(C)が両方あれば `total == T − C`。合計行がOCRで壊れた時の**復元/タイブレーク**に使う。
7. **割引**: `▲ / △ / 値引 / 割引 / クーポン / 末尾- / 括弧()` をマイナスとして認識し、**必ず割引後の `合計/お会計` を採る**。

### 7.3 日付抽出
1. 正規表現（正規化後テキスト）:
   - 西暦4桁: `(YYYY)[/\-.年](MM)[/\-.月](DD)日?`
   - 2桁年(サーマル): 境界要求 `(?<![\d/\-.])(YY)[/\-.](MM)[/\-.](DD)(?![\d/\-.])`
   - 和暦: `(令和|平成|昭和|R|H|S)\s*(元|\d{1,2})[年.\-/](MM)[月.\-/](DD)日?`
   - 時刻 `HH:MM` は分離（取引時刻の手がかりに使う）。
2. **和暦→西暦**: 令和=2018+N、平成=1988+N、昭和=1925+N（元=1）。例 `令和6年`=2024。**ラベル無しの `6.07.03` は和暦(令和6=2024)** の可能性が高い＝「1〜2桁年・世紀なし・今より~18年以上過去に落ちる」なら和暦推定して今日と整合をとる（`YY.MM.DD`→2006 の18年誤りを回避）。
3. **選択規則**:
   - カレンダー日付を構築して妥当性検証（`1≤m≤12`、`daysInMonth` 準拠、往復検証で 2/30 等を弾く）。
   - **未来日を棄却**（`today + 1日` 超）＝ ポイント有効期限・キャンペーン終了・賞味期限を除去。
   - 古すぎ（`year < 2000`）棄却＝ OCRゴミ/2桁誤読。
   - **発行日=単純な最上部ではなく取引手がかりで選ぶ**: `時刻HH:MM` / `レジ` / `No.` / `責任者` に近接する日付を優先。`セール期間 A〜B` や `有効期限/まで/期限` の行は除外。
   - **年欠落（MM/DDのみ）**: 今日を超えない直近の年を採用（12月購入を1月にスキャンして翌年扱いする誤りを回避）→ 低確信度。
   - 見つからなければ**今日**を既定・低確信度。

### 7.4 1レシート＝1取引・1カテゴリ（v1限界の明記）
実店舗レシートは 食費＋日用品＋医療 が混在するが、v1は**1レシート=1取引=1カテゴリ**。→ 限界として明記し、**「保存して続けて入力」で同じ日付/店名をプリフィルした分割入力を容易にする**。

### 7.5 確信度（規則ベース・説明可能）
「色分け」を曖昧にしない。**離散tier**にする:
- **high**: `合計/お会計` 等の総額ラベルと同一行で採用／日付が時刻と同居し取引手がかり近接。
- **medium**: ラベル無しのmaxフォールバック採用／年推定した日付。
- **low**: 候補なし・今日既定・裸数値のみ。
各tierを色にマップ。確認画面で該当欄をハイライトし、**候補が複数ある時は切替UI**を出す。

### 7.6 画像ライフサイクル（オフライン担保）
Apple Vision自体は端末内だが、**レシート写真も財務データ**。image_picker/カメラの取得先が共有フォトライブラリだと iCloud Photos で同期し得る。
→ **アプリ専用一時パスに取得（カメラロールに残さない）→ パース → 即削除**（保持設定ONの時のみ §14-C の imagePath に移動）。可能なら一時パスをiCloudバックアップ対象外に。

## 8. OCRサービス / プラットフォームチャネル（iOS実装は Mac）

### 8.1 Apple Vision（研究で裏取り済みの要点）
- `VNRecognizeTextRequest` + `VNImageRequestHandler(cgImage:orientation:)` をメインスレッド外で `perform`。結果 `[VNRecognizedTextObservation]`、各 `topCandidates(1).first` に `string` と `confidence`、observationに `boundingBox`（**正規化・左下原点**）。
- 設定: `recognitionLevel = .accurate`、`revision = ...Revision3`、`recognitionLanguages = ["ja-JP","en-US"]`、`usesLanguageCorrection = true`、`automaticallyDetectsLanguage = false`、`customWords = ["合計","小計","税込","税抜","お預り"]`、`minimumTextHeight = 0`。
- **日本語認識は iOS 16+（Revision3）が必須**。deployment target を iOS 16 に。`if #available(iOS 16.0, *)` でガードし、未満はチャネルでエラーを返す。
- **座標変換**: 正規化左下原点 → ピクセル左上原点へ **Y反転**（`y = (1 − by − bh) * H`）。向き(EXIF)をhandlerに渡すか、事前に `.up` へ焼き込み。§7.1 の正準空間へ写像。
- MethodChannel返却は `[[String:Any]]`（Dartで `List<Map>`）を推奨。`{text, x, y, w, h, confidence}`。

### 8.2 フィクスチャ橋渡し（自走テストの生命線）
- **記録レイヤを間違えない**: パーサが本番で食うのは**正準TextBlock**。橋渡しツールは **raw Vision出力と正準化後の両方**をスナップショットし、adapterのドリフトも検出する。
- **合成摂動レイヤ**を足す: 収集フィクスチャに OCRノイズ（O/0誤読、¥/P/ラベル落ち、行の結合/分割、傾き）を注入して、十数枚の綺麗なサンプルを超えてヒューリスティクスを stress する（自走テストの過信を防ぐ）。
- **順序**: 実装前に **Mac で実レシート ~15枚を一度 Vision に通して実フィクスチャを取得** → それに駆動されてパーサを調整（§13宿題）。手作りフィクスチャへの過学習を避ける。

```
lib/
  app/        … ルーティング, テーマ, main, DIルート(Riverpod)
  data/
    db/       … drift テーブル/DAO, マイグレーション, PRAGMA foreign_keys=ON
    repositories/ … TransactionRepository, CategoryRepository（署名・updatedAt・sourceを一元管理）
    backup/   … BackupService(JSON往復, 暗号化), CsvExporter(エクスポート専用)
  domain/
    services/ … OcrService(抽象), AppleVisionOcrService(iOS/MethodChannel), FakeOcrService(テスト),
                ReceiptParser(純Dart), TextBlock 正準モデル
    money/    … 署名/集計ヘルパ, civil date ユーティリティ
  features/   … calendar/ entry/ receipt/ summary/ settings/（画面 + Riverpod providers）
```

- リポジトリでDBを隠蔽。**全ての取引ミューテーションはリポジトリの単一チョークポイント**を通し、`updatedAt`・符号・`source`不変を保証。

- OCRは `OcrService` 抽象の裏。テストは `FakeOcrService`＋正準TextBlockフィクスチャ。**純Dartの `ReceiptParser` は iOS非依存でWindowsテスト可**。

## 10. バックアップ／復元 仕様（データ喪失防止の核心）

### 10.1 復元はアトミック（validate-then-swap）
全消し→投入の途中失敗（不正行・FK違反・ディスク満杯・iOSによるバックグラウンド強制終了）で**全損**する。
→ **手順**: (1) ファイル全体をメモリにパースし**完全検証** → (2) **単一driftトランザクション内で** delete-all → insert-all → commit。途中失敗は自動ロールバック。**新データが挿入可能と証明されるまで既存を消さない。**

### 10.2 復元前の自動退避（サイレント）
- 共有シートは使わず**アプリFilesへサイレント書き込み**（フルJSONのみ、CSV不可）。
- **削除の前にファイル存在＋再パース成功を検証**、失敗なら復元を中止。
- **タイムスタンプ付き・上書きしない**（連続した悪いインポートが最後の正常状態を消さない）。
- **「自動退避から復元」UI**で取り出せる（＝一発 Undo）。

### 10.3 検証（バージョン＋内容）
- `schemaVersion`: **等値でなく範囲**。古い版は現行形へ**前方マイグレーション**、**アプリより新しい版は拒否**、欠落/0は不正。
- 内容: amount=非負整数、type/paymentMethod=既知enum、date=妥当なcivil date、**全 categoryId が同梱カテゴリに解決**、空配列でないこと（空復元は明示確認）。1つでも違反なら**既存を保持して拒否**。

### 10.4 ID保存
- 復元はクリーンスレート置換なので**元IDを保存**。カテゴリを新IDで再挿入して取引の`categoryId`だけコピー、のような**FK取り違えを起こさない**。
- **後検証**: 復元後に全 `categoryId` が解決することをアサート。解決しない孤児は「未分類」へ再割当。
- 復元時は**プリセット再シードを無効化**。

### 10.5 CSV
- **エクスポート専用**（閲覧/分析）。**復元パスから除外**（単一テーブルでFK/属性を表現できず、schemaVersionも運べない）。
- RFC-4180 のクオート/エスケープ（memo/店名のカンマ・改行・引用符・絵文字）＋ **UTF-8 with BOM**（日本語Excelの文字化け回避）。Numbers/Excelで開いて往復確認。

## 11. エラー処理・エッジケース
- OCR空/低確信 → 空フォーム＋注記（金額欄フォーカス）。
- 合計が複数/曖昧 → ベスト推定＋ハイライト＋候補切替。
- 金額パース不能 → 空保存させない（バリデーション）。
- 未来/非現実日付 → 棄却し今日既定。
- カテゴリ型変更を取引存在下でブロック。型トグルで候補再フィルタ＋選択クリア。
- インポート各種失敗（§10）。
- 空状態（§5.5）。
- 画像取得キャンセル/権限拒否 → 手入力へフォールバック。

## 14. 確定した決定（承認済み 2026-07-03・すべて推奨採用）

技術修正（§4.2 civil date、§4.5 FK/未分類、§7 パーサ堅牢化、§10 アトミック復元 等）は正しさの問題として採用済み。以下の好み/哲学の4点もユーザー承認で確定。

**A. 「完全オフライン」の再定義とバックアップ（§2.1）— 最重要 ✅確定**
原則を「**アプリは財務データを自動/バックグラウンド/第三者/LLMに送信しない。ユーザー明示エクスポートのみ端末外へ**」に精密化。**オンデバイス自動バックアップ（共有シート不要・世代保持）＋「前回N日前」バナー＋任意パスフレーズ暗号化エクスポート**を入れる。手動のみは全損リスクのため不可。CloudKit同期はv1非対象（Phase 2候補）。

**B. paymentMethod（§4.1）✅確定**
**列はnullableで残す（将来マイグレーション不要）が、v1入力UIからは外す**。Summaryに内訳が無く分析価値ゼロ、既定=現金はカード/PayPay/Suica中心の実態に逆行するため。将来UIに出すなら既定=前回使用値。

**C. レシート画像の保持（§4.1 imagePath, §7.6）✅確定**
**既定は破棄**（プライバシー優先、カメラロールに残さない）。**設定で「再検証用にローカル保持」ONを用意**（imagePath使用、既定OFF）。

**D. サマリの置き場所（§5）✅確定**
**独立タブ維持（3タブ）**。入力(カレンダー)と振り返り(サマリ)は使う場面が別。
